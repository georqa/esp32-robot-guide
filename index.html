ESP32

Four parts, one loop: an ultrasonic sensor and an infrared array feed the ESP32, the ESP32 decides where to steer, and the L298N turns that decision into motor power.

01

HC-SR05 ultrasonic sensor

distance

Two round elements sit at the front of the HC-SR05: one sends out a short, high-frequency sound that people can't hear, and the other listens for its echo bouncing off whatever is in front of it — the same principle a bat uses to find its way in the dark.

The ESP32 triggers a measurement, then times how long the sound takes to make the round trip. Because it travels to the object and back, the distance calculation divides by two:

distance = speed of sound × time ÷ 2

A 2 ms round trip works out to roughly 34 cm.

5 Vsupply
2–450 cmrated range
ECHO ≈ 5 Vneeds a divider

Where it earns its place

On a sumo robot it spots the opponent ahead; on a robot exploring open ground it triggers obstacle avoidance — once the distance drops below a threshold, the program tells the motors to stop or turn.

Wiring note: the sensor's ECHO output can swing up to 5 V, but the ESP32's GPIO pins only tolerate 3.3 V. A voltage divider between ECHO and the ESP32 input is required. The sensor also can't identify what it's detecting, and angled or sound-absorbing surfaces make readings less reliable.
02

Five-channel IR sensor

line position

Mounted low at the front of the robot, this bar has five infrared sensing positions spanning left to right. Each one shines infrared light at the floor and measures how much bounces back — white surfaces reflect more than a black line, so as the sensor drifts across the line, the five readings shift with it.

Line positionRobot response
CentreDrive straight ahead
LeftSteer left
RightSteer right
Outside sensor rangeSearch for the line per program logic

Steering happens by changing motor speeds rather than jerking a wheel — if the line drifts left, the program slows the left motor or speeds up the right one. Many small corrections per second let the robot trace a curve smoothly.

Measured on this robot: the middle channel read ~3888 over white and ~1360 over black — lower means "on the line" here, but each of the five channels should be calibrated separately, since they don't always agree. Mounting height, ambient light, and floor material all shift the numbers, so it's worth measuring white and black on the actual track before a run.
03

L298N motor driver

power

An ESP32 pin can't supply the current a motor needs — that's the L298N's job. It sits between the ESP32 and the motors, taking low-power direction and speed commands and switching real motor current in response. One board handles two DC motors independently, enough for a two-wheel line-follower or sumo bot.

Two H-bridges, one per motor

MotorDirection pinsOutputSpeed control
AIN1, IN2OUT1, OUT2ENA
BIN3, IN4OUT3, OUT4ENB

Flipping the two IN pins for a motor reverses its direction. Speed is set with a PWM signal on ENA or ENB — switching the motor on and off fast enough that the proportion of "on" time sets the average speed. When the IR array sees the line drifting left, the ESP32 tells the L298N to slow the left motor while the right one keeps turning, and the robot arcs left.

Wiring note: motors connect to the OUT pins, never directly to an ESP32 GPIO. The ESP32 and L298N need a shared ground so control signals read correctly, and some of the motor's power is lost as heat inside the L298N — so motor voltage runs a little below battery voltage.
04

ESP32 — the brain

controller

The ESP32 is the microcontroller running the robot's program: it reads the sensors, decides what to do, and issues commands to everything else. Most boards expose a USB port for programming and a row of GPIO pins for wiring in the rest of the circuit.

ComponentWhat it exchanges with the ESP32
Five-channel IR sensorReports the black line's position
HC-SR05 ultrasonic sensorReports distance to an obstacle
ESP32Processes both readings and decides the move
L298N motor driverReceives the movement command, drives the motors

Say the IR array sees the line drift left — the ESP32's program tells the L298N to change motor speeds, the robot turns left, and the whole cycle repeats many times a second so the robot keeps correcting its path.

Beyond the sensor loop

Built-in Wi-Fi and Bluetooth let the ESP32 take commands wirelessly too — a remote-controlled build might read button presses from a web page on a phone. It can also read analog sensor values directly and generate the PWM signals that set motor speed.

Wiring note: ESP32 GPIOs run on 3.3 V logic — always check a sensor's output voltage before wiring it in, since a 5 V signal will damage a 3.3 V pin. Motors need their own driver and power supply and should never connect straight to a GPIO.
// REFERENCE SKETCH

How it runs, in code

One Arduino sketch for the ESP32: it reads the five IR channels and the HC-SR05, decides whether to follow the line or dodge an obstacle, and drives the L298N accordingly. Pin numbers and calibration values are placeholders — swap in the ones measured on your own robot.

robot_loop.ino
// ESP32 + HC-SR05 + 5-ch IR array + L298N
// Obstacle avoidance takes priority; otherwise, follow the line.

const int TRIG_PIN = 5;
const int ECHO_PIN = 18;      // through a voltage divider: 5V -> 3.3V

const int IR_PINS[5] = {32, 33, 34, 35, 36};  // left to right
const int IR_BLACK_THRESHOLD = 2000;           // below this = line seen

const int IN1 = 27, IN2 = 26, ENA = 14;  // left motor
const int IN3 = 25, IN4 = 23, ENB = 13;  // right motor  (choose free pins)

const int BASE_SPEED = 180;    // 0-255 PWM
const int TURN_SPEED  = 120;
const float STOP_DISTANCE_CM = 15.0;

void setup() {
  Serial.begin(115200);
  pinMode(TRIG_PIN, OUTPUT);
  pinMode(ECHO_PIN, INPUT);
  for (int i = 0; i < 5; i++) pinMode(IR_PINS[i], INPUT);

  pinMode(IN1, OUTPUT); pinMode(IN2, OUTPUT); pinMode(ENA, OUTPUT);
  pinMode(IN3, OUTPUT); pinMode(IN4, OUTPUT); pinMode(ENB, OUTPUT);
}

void loop() {
  float distance = readDistanceCM();

  if (distance > 0 && distance < STOP_DISTANCE_CM) {
    avoidObstacle();
  } else {
    followLine();
  }
}

// ---- HC-SR05: trigger a ping, time the echo, convert to cm ----
float readDistanceCM() {
  digitalWrite(TRIG_PIN, LOW);  delayMicroseconds(2);
  digitalWrite(TRIG_PIN, HIGH); delayMicroseconds(10);
  digitalWrite(TRIG_PIN, LOW);

  long duration = pulseIn(ECHO_PIN, HIGH, 30000);  // 30ms timeout
  if (duration == 0) return -1;                    // no echo received
  return (duration * 0.0343) / 2.0;                 // distance = speed x time / 2
}

// ---- Five-channel IR array: find the line and steer toward it ----
void followLine() {
  int reading[5];
  for (int i = 0; i < 5; i++) reading[i] = analogRead(IR_PINS[i]);

  bool onBlack[5];
  for (int i = 0; i < 5; i++) onBlack[i] = reading[i] < IR_BLACK_THRESHOLD;

  if (onBlack[2]) {
    driveMotors(BASE_SPEED, BASE_SPEED);           // centred: go straight
  } else if (onBlack[0] || onBlack[1]) {
    driveMotors(TURN_SPEED, BASE_SPEED);           // line to the left: turn left
  } else if (onBlack[3] || onBlack[4]) {
    driveMotors(BASE_SPEED, TURN_SPEED);           // line to the right: turn right
  } else {
    driveMotors(TURN_SPEED, -TURN_SPEED);          // line lost: spin and search
  }
}

// ---- Obstacle in range: stop, then turn away from it ----
void avoidObstacle() {
  driveMotors(0, 0);
  delay(150);
  driveMotors(TURN_SPEED, -TURN_SPEED);            // pivot right; adjust to taste
  delay(300);
}

// ---- L298N: set direction on IN pins, speed on EN pins (PWM) ----
void driveMotors(int leftSpeed, int rightSpeed) {
  digitalWrite(IN1, leftSpeed  >= 0 ? HIGH : LOW);
  digitalWrite(IN2, leftSpeed  >= 0 ? LOW  : HIGH);
  analogWrite(ENA, abs(leftSpeed));

  digitalWrite(IN3, rightSpeed >= 0 ? HIGH : LOW);
  digitalWrite(IN4, rightSpeed >= 0 ? LOW  : HIGH);
  analogWrite(ENB, abs(rightSpeed));
}
Before you flash this: re-measure IR_BLACK_THRESHOLD against your own track's black line and white background, confirm the GPIO numbers against your specific ESP32 board, and double-check the HC-SR05's ECHO line is running through a voltage divider — not straight into a GPIO.
// WI-FI REMOTE CONTROL

Drive it from a web page

This sketch turns the ESP32 into its own Wi-Fi access point and web server: it serves a page with FORWARD / LEFT / STOP / RIGHT / REVERSE buttons and a speed slider, and drives the L298N directly from button presses instead of the sensors.

wifi_control.ino
#include <WiFi.h>
#include <WebServer.h>

// Replace with your network credentials
const char* ssid     = "esp32";
const char* password = "1000Limni";

int motor1Pin2 = 26;

int motor2Pin2 = 25;

// Setting PWM properties
const int freq = 30000;
const int resolution = 8;
int dutyCycle = 0;

String valueString = String(0);

void handleForward() {
  Serial.println("Forward");
  digitalWrite(motor1Pin1, LOW);
  digitalWrite(motor1Pin2, HIGH); 
  digitalWrite(motor2Pin1, LOW);
  digitalWrite(motor2Pin2, HIGH);
  server.send(200);
}

void handleLeft() {
  Serial.println("Left");
  digitalWrite(motor1Pin1, LOW); 
  digitalWrite(motor1Pin2, LOW); 
  digitalWrite(motor2Pin1, LOW);
  digitalWrite(motor2Pin2, HIGH);
  server.send(200);
}

void handleStop() {
  Serial.println("Stop");
  digitalWrite(motor1Pin1, LOW); 
  digitalWrite(motor1Pin2, LOW); 
  digitalWrite(motor2Pin1, LOW);
  digitalWrite(motor2Pin2, LOW);   
  server.send(200);
}

void handleRight() {
  Serial.println("Right");
  digitalWrite(motor1Pin1, LOW); 
  digitalWrite(motor1Pin2, HIGH); 
  digitalWrite(motor2Pin1, LOW);
  digitalWrite(motor2Pin2, LOW);    
  server.send(200);
}

void handleReverse() {
  Serial.println("Reverse");
  digitalWrite(motor1Pin1, HIGH);
  digitalWrite(motor1Pin2, LOW); 
  digitalWrite(motor2Pin1, HIGH);
  digitalWrite(motor2Pin2, LOW);          
  server.send(200);
}

void handleSpeed() {
  if (server.hasArg("value")) {
    valueString = server.arg("value");
    int value = valueString.toInt();
    if (value == 0) {
      ledcWrite(enable1Pin, 0);
      ledcWrite(enable2Pin, 0);
      digitalWrite(motor1Pin1, LOW); 
      digitalWrite(motor1Pin2, LOW); 
      digitalWrite(motor2Pin1, LOW);
      digitalWrite(motor2Pin2, LOW);   
    } else { 
      dutyCycle = map(value, 25, 100, 200, 255);
      ledcWrite(enable1Pin, dutyCycle);
      ledcWrite(enable2Pin, dutyCycle);
      Serial.println("Motor speed set to " + String(value));
    }
  }
  server.send(200);
}

void setup() {
  Serial.begin(115200);

  // Set the Motor pins as outputs
  pinMode(motor1Pin1, OUTPUT);
  pinMode(motor1Pin2, OUTPUT);
  pinMode(motor2Pin1, OUTPUT);
  pinMode(motor2Pin2, OUTPUT);

  // Configure PWM Pins
  ledcAttach(enable1Pin, freq, resolution);
  ledcAttach(enable2Pin, freq, resolution);
    
  // Initialize PWM with 0 duty cycle
  ledcWrite(enable1Pin, 0);
  ledcWrite(enable2Pin, 0);
  
  // Connect to Wi-Fi
  Serial.print("Connecting to ");
  Serial.println(ssid);
  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.println("");
  Serial.println("WiFi connected.");
  Serial.println("IP address: ");
  Serial.println(WiFi.localIP());

  // Define routes
  server.on("/", handleRoot);
  server.on("/forward", handleForward);
  server.on("/left", handleLeft);
  server.on("/stop", handleStop);
  server.on("/right", handleRight);
  server.on("/reverse", handleReverse);
  server.on("/speed", handleSpeed);

  // Start the server
  server.begin();
}

void loop() {
  server.handleClient();                 
}
Before you flash this: change ssid and password to your own, and note it drives motors straight from IN1–IN4 with no sensor input at all — obstacle avoidance and line-following are switched off while this sketch is running.
// SUMO ROBOT

Sumo Robot

An autonomous vehicle that competes inside a circular dohyo: find the opponent, push it out, don't cross the edge yourself. Same three parts as the guide — ultrasonic sensor, ESP32, L298N — with an added IR pair watching the boundary.

01

What a Sumo Robot needs

overview

It competes autonomously — once the match starts, nobody drives it. It reads its sensors, decides, and moves entirely on its own. A basic build adds only a little to the parts already on the guide page:

  • an ESP32 microcontroller
  • an L298N motor driver
  • an ultrasonic distance sensor, aimed forward at the opponent
  • one or two IR sensors facing the floor, for the arena boundary
  • two geared DC motors, wheels, and a caster wheel
  • a battery, chassis, and — traditionally — a low wedge at the front

Everything reduces to three stages repeated many times a second: input (sensors collect readings), processing (the ESP32 decides), output (the L298N moves the motors).

02

What the ESP32 decides

logic

The ESP32 triggers the ultrasonic sensor, times the echo, reads the boundary sensors, and picks a movement — then does it again. In plain terms, its rules look like:

  • no opponent detected → rotate and keep searching
  • opponent detected close by → drive forward fast
  • near the arena boundary → break off the attack and move away
Wiring note: the ESP32 reads at 3.3 V logic, but some ultrasonic sensors put out a 5 V ECHO signal — route it through a voltage divider or logic-level converter before it reaches a GPIO.
03

Finding the opponent

ultrasonic

Four pins do the work: VCC, GND, TRIG to fire a pulse, ECHO to report how long it took to come back. The ESP32 times that round trip and converts it to a distance:

distance = (speed of sound × time) ÷ 2
< 30–40 cmtypical attack threshold
narrowdetection field — one direction at a time

Because the sensor only "sees" a narrow cone, an empty reading doesn't mean an empty arena — it means the robot should rotate and check somewhere else.

04

Turning decisions into movement

L298N

Same driver, same idea as on the guide page: IN1/IN2 and ENA run the left motor, IN3/IN4 and ENB run the right one, and PWM on the EN pins sets speed.

05

States, then the loop

behaviour

Start delay — a short pause after power-on, so the operator can clear the dohyo before autonomous control begins.

Search — no object in range: the robot rotates, re-measuring continuously, until something appears within the attack distance.

Detection and attack — distance drops below the threshold: both motors go forward at speed. A wedge at the front can slide under the opponent and cut its traction.

Boundary avoidance — the ultrasonic sensor only looks ahead, so it can't see the arena's edge; that's the IR pair's job. When they see the white boundary line, the robot stops, reverses, turns back toward the centre, and resumes searching.

Priority matters: boundary avoidance always outranks attack. Even mid-charge, the robot checks the edge first — staying inside the dohyo is a safety rule, not an optional extra.

The cycle, every pass

  1. Check the boundary sensors.
  2. White line seen → escape move (back up, turn in).
  3. Otherwise, take a distance reading.
  4. Opponent in range → drive toward it.
  5. Nothing in range → rotate and keep searching.
  6. Repeat, many times a second.
ConditionDecisionMovement

Opponent at short distanceAttackFast forward
Opponent at greater distanceApproachForward

06

What actually decides a match

tuning
  • ultrasonic accuracy, plus the sensor's mounting angle and position
  • motor speed and battery charge
  • wheel traction and how weight is distributed
  • wedge height at the front
  • how fast the program can loop
A small, angled, or very close surface can scatter the ultrasonic echo away from the sensor rather than back to it, and firing measurements too rapidly can return noisy readings. Taking several readings and discarding outliers makes detection steadier.
// LINE-FOLLOWING ROBOT

Line-Following Robot

A closed-loop system: the five-channel IR sensor reports where the line is, the ESP32 corrects, the L298N adjusts each wheel's speed — many times a second, so small drifts never become big ones.

01

What it takes to build one

overview

A line-following robot tracks a path — usually a black line on a white floor — by continuously sensing where the line sits under it and correcting its heading. It's a textbook automation loop: input, processing, output.

  • an ESP32 microcontroller
  • an L298N motor driver
  • a five-channel infrared (IR) sensor
  • two geared DC motors, two wheels, a caster wheel, and a battery
02

What the ESP32 does

logic
  • reads all five IR channels
  • works out where the black line sits under the robot
  • decides: straight, left, or right
  • sets each motor's speed with PWM
  • stops when the line is lost or the route ends

Higher PWM roughly means higher average voltage at the motor, and so more speed — the same mechanism used for direction and speed everywhere else on this site.

Wiring note: ESP32 GPIOs read 3.3 V logic. Keep sensor outputs at or under that, with a divider or level converter if they run at 5 V.
03

Five channels, one line

IR array

The five sensors sit in a row across the front-underside of the robot, each with its own emitter and receiver, named left to right:

ChannelPosition
IR1Left outer
IR2Left inner
IR3Centre
IR4Right inner
IR5Right outer

White floor reflects most of the infrared light back; the black line absorbs more of it and reflects less — that contrast is what each receiver measures. Depending on the board, the output may be a simple digital 0/1 per channel or an analog value with finer resolution.

Don't assume the polarity: black doesn't always read as "0" — it depends on the specific board's circuit. Measure both surfaces on your own sensor and calibrate a threshold before relying on it.
04

Turning a reading into a turn

L298N

The wiring is the same L298N setup as the guide page — IN1–IN4 for direction, ENA/ENB for PWM speed. What changes here is which channel drives the correction:

Line positionMovementLeft motorRight motor
IR1Strongly leftVery slow / stoppedFast
IR2Slightly leftSlowFast
IR3StraightNormalNormal
IR4Slightly rightFastSlow
IR5Strongly rightFastVery slow / stopped

The speed gap between the two wheels is what actually steers the robot — the farther off-centre the line, the bigger that gap should be.

05

The control loop, and calibrating it

feedback
  1. Read the five sensors.
  2. Compare each against a threshold.
  3. Work out the line's position.
  4. Pick a movement.
  5. Send new speeds to the L298N.
  6. Repeat, many times a second.

This is closed-loop feedback control: the sensors keep telling the ESP32 the result of its last move, so any drift gets corrected almost as soon as it happens. A simple version just follows fixed rules (center → straight, left → turn left, and so on); a PID controller instead measures how far off-centre the line is and scales the correction to match, which tends to produce a smoother path with less side-to-side hunting.

floor & lightshift sensor readings
line widthaffects detection
motor matchuneven motors curve the path
If it zig-zags: that's usually excess speed, over-strong correction, or a threshold that wasn't calibrated on the actual track. Slow the base speed and soften the correction before changing anything else.
